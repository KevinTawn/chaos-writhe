# 混乱与蠕动 · 本地联机版

把原来的单文件热座战棋《混乱与蠕动》改造成 **服务器权威 + WebSocket 实时同步** 的双人联机游戏，同时保留单机热座；圣辉之战、蛇骨矿洞、蠕潮蚀野、烽燧阵线与霓虹纪元在联机版和单机热座中都可直接游玩。

- 当前应用版本：`2.1.0`；规则版本：`v5.6`（与 `../现行版本/同步更新单机版.html` 一致）
- 支持模式：经典、雪原群狼之舞、城邦裂变、海盗港湾、雾夜幽乡、圣辉之战、蛇骨矿洞、蠕潮蚀野、烽燧阵线、霓虹纪元
- 模式归属：**10 种模式在联机版与单机热座中全部开放**；单机热座可直接测试圣辉天空层、矿洞地下层、蠕潮蚀野、烽燧阵线与霓虹纪元
- 运行方式：本机 / 局域网，Node.js + `ws`，无需数据库

---

## 快速开始

```bash
# 首次运行
npm install

# 启动服务器（默认 3000 端口）
npm start

# 或指定端口
PORT=3000 node server/server.js
```

浏览器打开：

| 地址 | 用途 |
|------|------|
| `http://localhost:3000` | 联机大厅 |
| `http://localhost:3000/local` | 单机热座（10 种模式，含圣辉天空层、矿洞地下层、蠕潮蚀野、烽燧阵线与霓虹纪元；含关卡战役） |
| `http://localhost:3000/codex` | 战地图鉴（兵种 / 技能卡 / 配乐试听） |
| `http://localhost:3000/rules` | 完整游玩规则 |
| `http://localhost:3000/copyright` | 版权信息（开发者：前进四） |

两名玩家可以：

- 在同一台电脑上开**两个浏览器窗口**即可（会话按标签页隔离，互不串号；浏览器内刷新仍可重连）；
- 在局域网内，用 `http://<本机内网IP>:3000` 分别访问。

> Windows 首次启动可能弹出防火墙提示，需要允许 Node.js 访问专用网络，局域网设备才能连接。

联机流程：房主选择模式 → 创建房间 → 把 6 位房间号发给对手 → 对手加入 → 双方点「准备」→ 开始部署。

## 架构与实现要点

```
玩家A浏览器 ←→ WebSocket ←→ Node 服务器（权威 gameState） ←→ WebSocket ←→ 玩家B浏览器
```

### 1. 规则逻辑原样复用

`shared/gameEngine.js` 不是重写版，而是把单机版 `<script>` 中的规则函数**原样切出**，只替换了：

- DOM 渲染函数 → `renderAll()` 通知服务器广播；
- `addLog` 写 DOM → 收集到日志数组；
- 抽卡弹窗 / 胜负浮层 / 炮弹动画 → 服务端生成 `drawChoices`、`gameOver`、`fx` 事件；
- 全局单例 → `createGameEngine()` 工厂，每个房间一个独立实例。

战斗判定表、技能卡结算、模式事件、波斯远征军/鬼 AI、回合流程均与单机版一致。规则来源可追溯：`tools/extract-engine.cjs` 按函数/注释标记从 `client/local/app.js` 抽取（不依赖行号，单机版加样式或动画不会破坏抽取）。

### 2. 客户端不持有判定逻辑

客户端只负责：

- 渲染服务器下发的**个人可见状态**；
- 把点击/按钮翻译成指令；
- 播放纯表现动画（炮弹、日志滚动）。

可移动/可攻击格由服务器用原版 `getUnitActionTiles()` 计算后下发（`view.actionTiles`），技能合法目标由服务器用原版 `skillCandidates()` 计算后下发（`view.skillTarget.validTiles`）。客户端不做任何合法性推断。

### 移动动画（单机 + 联机，纯表现）

两版使用同一套差分动画。联机版对比服务器前后状态；单机版对比前后两次渲染的快照，并在同一次操作触发的多次同步重绘时合并为末尾一次播放。

- 直线 / 相邻斜向移动：单位从旧格连续滑到新格，并在途经格留下短暂残影；
- 跃迁、换位等非直线远距离移动：旧位置淡出、新位置淡入；
- 新单位出现、单位被消灭：淡入 / 淡出；
- 波斯远征军和初晖鬼魂的 AI 每次一格移动同样触发，因为 AI 每步都会广播新状态；
- 雾夜隐藏的鬼魂和未揭示的地雷不参与动画，避免通过动画泄露隐藏信息；
- 落点、路径完全由服务器状态决定，动画不参与任何判定。

### 程序化背景音乐（1.6.0 起，1.8.0 希腊化、正式版重写与结束曲）

- **来源与结构**：`client/music.js` 是唯一音乐源，用 Web Audio 振荡器 / 噪声 / FM 钟声实时合成，不加载任何音频文件；联机版直接引用，单机版由 `tools/build-local.cjs`（`npm run build:local`）内联进离线单文件，保持无外部依赖。
- **十一段循环**：大厅（lobby，32 小节）、经典战场（battle，112 BPM，48 小节）、城邦裂变·行军（wannan，84 BPM，32）、城邦裂变·事变后（wannan2，126 BPM，6/8，48）、雪原（snow，32）、海盗（pirate，16）、雾夜幽乡（fog，16）、圣辉（holy，32）、蛇骨矿洞（mine，108 BPM，6/8，32）、蠕潮蚀野（tide，32）、烽燧阵线（beacon，96 BPM，32，中国大鼓、低音笙式奥洛斯、古筝式拨弦与号角长音）。经典与城邦二阶段采用 A–B–A′–C–D–coda 六段体，其余沿用 8 小节 A/B 素材拼接；切换场景时淡出旧曲再起新曲，同一场景内的天候变化不重排旋律。
- **九段模式结束曲**：每局进入 `gameOver` 时按模式切到两小节的明亮小曲，`once: true`，播完最后一步即停止调度并让混响自然收尾，不会循环。九段都采用「上行旋律 + 主和弦收尾 + 高音铃」的关卡通过式写法，并按模式换主奏音色与调性：
  - `end_battle`（经典，138 BPM，C 大调，2 小节）：铜管奏 C–E–G–C 号角，太鼓、定音鼓与军鼓滚奏收尾；
  - `end_snow`（雪原，126 BPM，F 大调，2 小节）：钢片琴式拨弦与高音钟上行，末尾 F 和弦加雪晶铃音；
  - `end_city`（城邦裂变，132 BPM，D 大调，2 小节）：里拉琴琶音与奥洛斯管凯歌，框鼓与定音鼓收住；
  - `end_pirate`（海盗，150 BPM，G 大调，2 小节 6/8）：提琴吉格跳跃音型，沙锤与太鼓推动；
  - `end_fog`（雾夜，120 BPM，A 大调，2 小节）：钟声与拨弦踩着切分音上升，合唱垫亮出 A 和弦；
  - `end_holy`（圣辉，128 BPM，B♭ 大调，2 小节）：合唱与提琴上行，铜管、定音鼓给出庄严的终止；
  - `end_mine`（蛇骨矿洞，126 BPM，E♭ 大调，2 小节）：拨弦与远钟在低频垫上蹦跳，太鼓砸出主和弦；
  - `end_tide`（蠕潮，120 BPM，E 大调，2 小节）：奥洛斯管与水滴铃音上行，低音鼓稳住潮汐后收在主和弦；
  - `end_beacon`（烽燧阵线，104 BPM，2 小节）：中国大鼓与号角上行，末尾以古筝式拨弦与高音铃收束。
  结束曲会旁路天候低通与雨/风声，保证终局听感清晰；回到大厅、再来一局或重开对局后恢复对应循环。
- **城邦裂变专属曲**：84 BPM、32 小节，D 多利亚调式，和声为 Dm – C – B♭ – Am。里拉琴分解和弦铺底，奥洛斯管演奏 A/B 主题，框鼓与定音鼓标记行进，第二段加入低音铜管与合唱；不再使用二胡与皖南音阶。
- **经典战场·进行曲版**：112 BPM、4/4、48 小节，D 小调，A–B–A′–C–D–coda。D–F–A 起句的 8 小节主题由拨弦与提琴呈现，B 段转入小调属和声，C 段收成提琴主奏与低音，D 段全奏回到高音区，coda 重现主题；经典五种天候仍作用于该曲，并加入微风高音拨弦、薄雾低音钟与细雨沙锤的轻量换气加花。
- **城邦裂变二阶段（事变后）·抒情版**：`gameState.incidentTriggered`（联机为 `view.incident.triggered`）变真时切到 `wannan2`：126 BPM、6/8、48 小节，D 小调与弗里吉亚色彩，A–B–A′–C–D–coda。D–E♭–D–C 主题先由奥洛斯管在里拉琴引子后奏出，B 段抬高并加入合唱，A′ 用提琴低八度加厚，C 段收成低声区，D 段以高音、铜管、合唱与定音鼓展开，coda 回到主题收束。
- **蛇骨矿洞·音乐盒版**：108 BPM、6/8、32 小节，D 小调。拨弦与高音铃奏音乐盒式主题，低音持续音、风声与太鼓心跳铺底，B 段加入合唱，末段奥洛斯管在低音区回应；对应 1.7.0 矿洞地下层。
- **蠕潮蚀野曲**：56 BPM、32 小节，A 小调/爱奥利亚色彩。深色长音与低音持续音构成潮汐呼吸，潮眼心跳用低音鼓偏移重音，水滴用铃音与高音拨弦，水下合唱每 8 小节涌起一次；A/B 段旋律由里拉琴式拨弦与低音奥洛斯管交替。
- **按模式联动的天候层**：经典五种天候调整全局低通、雨声与微风声场，进行曲版另有轻量加花；雪原小雪 / 大雪叠加连续雪原风雨并加大低频鼓点；海盗东风 / 西风把整段混音偏向一侧并改变风声；雾夜 / 初晖切换钟声与低通。雨、风为持续噪声床，只改增益与声像，不会断断续续。
- **开关与解锁**：受浏览器自动播放策略限制，首次点击或按键后才开始发声。大厅顶部与对局顶部各有一个「♪ 音乐」按钮（文案在「音乐 / 静音」间切换），状态写入 `localStorage` 的 `chaos-music-enabled`；联机 `syncMusic()` 与单机 `renderAll` 包装把 `模式 + 天候 + 事变阶段 + gameOver` 同步给音乐模块，不改动规则区。
- **调试钩子**：`window.ChaosMusic.debug()` 返回就绪、开关、当前曲目、是否仍在调度、步进、曲长、天候键、低通截止频率与雨/风/声像数值，便于本地核对；`npm run test:music`（42 项）覆盖八段结束曲映射、只播一次、天候旁路、三首正式版曲目曲长与独立试听页曲目。

- 单位型技能卡（增益、混乱、压制、说服、缴获、替换、移除等）的单位候选取「地面全部可见单位 + 矿洞中对该选择方可见的单位」；视野外敌方矿洞单位不可选，联机 `getView.skillTarget.validTiles` 也不下发这些坐标。位置类效果仍限定地面层。
- 矿洞后勤兵可治疗相邻混乱友军，治疗格以 `heal` 行动返回；矿洞地图使用 2.5D 透视沙盘与地面同款的逐行缩放、边缘淡出和立体棋牌。
- 下井/上井只消耗指挥点、不消耗单位行动；若这次跨层消耗了最后 1 点指挥点且己方已无可行动单位，会立即自动结束回合。
- 胜负采用常规全灭，第 20 回合按存活战斗单位总数 → 地面单位数 → 技能点判定。单机热座同样开放矿洞模式，电脑对手只操作地面层。

### 3. 隐藏信息过滤

服务端在 `getView(viewerSide)` 中为每个玩家生成独立视图：

- **敌方地雷**：直接不发送；伪装地雷（技能 72）只发送一个假的「防御工事」外观。己方地雷正常可见。联机版已移除手动「查看地雷」按钮，服务端也会拒绝 `reveal/mines` 指令；只有排雷兵/工兵探测或技能揭示时才会对使用者显示，到期自动重新隐藏。单机热座保留原「查看地雷」按钮。
- **敌方手牌**：只发送 `libraryCount`，不发送卡牌 ID；抽卡候选只发给当前行动方。
- **雾夜鬼魂**：雾夜时不发送鬼魂单位；联机版不提供「查看鬼魂」，撞鬼当回合该鬼魂对双方显形；初晖时对所有人可见。单机版保留的 👻 按钮仅用于测试。
- **对方部署**：联机版双方同时部署，部署阶段完全不发送对方的红/蓝单位；双方都点击「完成部署」后统一揭示，地雷仍然隐藏。联机版不提供「查看敌方」按钮。单机热座保持红方先部署、蓝方后部署。
- **抽卡日志**：只播报「获得一张技能卡」，不播报卡名；「间谍渗透」也只播报复制成功，不公开具体卡名，避免日志泄露手牌。
- **技能目标**：未揭示的敌方地雷与雾夜鬼魂不会出现在合法目标/目标高亮中；使用查看类技能揭示后才可选择。

### 4. 断线重连

- 创建/加入房间时服务器返回随机 `token`，客户端存入 `sessionStorage`（按标签页隔离，两个窗口可各自扮演一方）；主动离开后 token 会保留，可从大厅「回到之前的房间」或重新输入房间号回到原席位；关闭整个标签页后，同一浏览器再次输入房间号可从「恢复上次的席位」弹窗选择红/蓝方返回；
- 刷新或断网后自动 `rejoin`，服务器校验 token 后绑定新连接并下发完整状态；
- 对手断线时另一方继续看到棋盘，并显示「对手：等待重连…」；
- 双方都离线后房间保留一段时间（未结束 30 分钟，已结束 10 分钟）再回收；
- AI 回合中的计时器独立于连接，重连不会中断波斯远征军/鬼的行动。

### 4.1 再来一局（交换先后手）

- 终局浮层新增「🔁 再来一局」；任一方先点击时服务器记录该席位（`room.rematch`），并提示等待对手确认；
- 双方都确认后服务器交换 `room.players.red/blue` 两个玩家对象，把各自连接绑定到新席位，再沿用 `room.mode` 重新 `startGame`；
- 客户端收到新的 `joined` 会更新 `session.side/token`，因此交换后「我」变成对方颜色，按钮、视野、可行动方都随之更新；
- 单机热座同样提供「再来一局（交换先手）」，在 `createInitialGameState().startingSide` 中记录本局先手，下一局红蓝部署与首个行动方对调；
- 对手已离开时不允许发起再来一局。

### 4.2 卡牌详情与记录导出

- `shared/constants.js` 由构建脚本从 `client/local/app.js` 同步导出 `CARD_KEYWORD_HELP`（关键词口径）与 `CARD_NOTES`（易混卡牌补充说明）；
- 联机牌库、手牌、抽卡候选和单机牌库、抽卡候选都可打开详情弹层；详情只使用客户端已有的卡牌常量与描述，不向服务器请求额外信息，因此不会泄露对手手牌；
- 终局「📄 导出本局记录」在浏览器本地生成 txt：时间、房间/模式、我方阵营、回合、结果、当前可见单位、最近日志。日志本身受视角过滤，不会包含对手手牌或隐藏地雷。

### 4.3 单机电脑对手与悔棋

- 模式选择勾选「🤖 单人练习」后，`gameState.aiSide='blue'`，一个 420ms 的本地调度器负责：蓝方军火库跳过、蓝方部署、蓝方行动、蓝方技能目标选择（如雪原“另起炉灶”）；联机版不加载这段逻辑；
- AI 行动使用引擎现有函数（`tryAttack/tryMove/chariotAttack/chariotMove/resolveArtilleryAttack/tryRemoveChaos`），不读取隐藏地雷，也不会使用技能卡；
- 悔棋在本地保存 `skillClone(gameState)` + 日志快照（最多 40 步），覆盖部署、移动、攻击、炮击、工兵建造/拆除、医疗、抽卡、用卡；AI 回合与终局不可悔棋；悔棋会清除尚未触发的模式事件计时器并恢复抽卡/选目标界面；
- 这两项均为单机版能力，`gameEngine.js` 中通过 `typeof pushUndo === 'function'` 守卫，服务端不会执行任何悔棋/AI 代码。

### 5. 房间与指令校验

- 房间号 6 位（去除易混淆字符），内存 `Map` 存储；
- 每个指令都在服务端校验阵营、回合、阶段、资源、目标合法性；
- 非当前行动方发送指令会收到 `error`，不会改变状态；
- 投降指令 `surrender` 不受回合/阶段限制，任一方随时生效；结算后重复投降返回 `error`；
- 房间内每方一个连接；同一 token 重连会顶掉旧连接；
- 大厅「重置大厅状态」只清除本标签页的 session（sessionStorage），不删除浏览器保存的席位 token（仍可输入房间号恢复）；旧房间由服务器超时回收。

## 公网部署

联机服务器是单进程 Node + `ws`，对局状态保存在内存中；部署后同一个地址既能打开网页，也能建立 WebSocket。

### Docker（推荐）

```bash
cd 混乱与蠕动联机版
docker compose up -d --build
# 本机验证
curl http://localhost:3000/health
```

镜像只包含 `server/`、`shared/`、`client/` 与运行依赖 `ws`（`Dockerfile`），不含 Electron 桌面壳。`docker-compose.yml` 默认映射 3000 端口，并每 30 秒检查 `/health`。

### 反向代理 + HTTPS/WSS

公网一定要用 HTTPS：客户端会自动把 `https://` 页面上的连接切成 `wss://`。仓库提供 `deploy/nginx.conf.example`，关键点是：

```nginx
proxy_http_version 1.1;
proxy_set_header Upgrade $http_upgrade;
proxy_set_header Connection $connection_upgrade;
proxy_read_timeout 3600s;   # 对局可能长时间没有消息
```

把示例里的域名、证书路径换成自己的，然后：

```bash
sudo cp deploy/nginx.conf.example /etc/nginx/conf.d/chaos-writhe.conf
sudo nginx -t && sudo systemctl reload nginx
```

### 注意事项

- 服务器重启会丢失进行中的对局（房间在内存里）；正式运营建议配合容器 `restart: unless-stopped`，并在低峰期更新。
- 单个进程即可支撑小规模对战；如需多实例，需要额外的房间路由/共享存储，当前版本未做。
- `DEV_DEBUG=1` 仅供本地自动化测试，会开放在服务端发牌 / 生成单位的测试指令；当 `AUTH_MODE` 不是 `dev` 时服务端会直接拒绝启动，避免误开成后门。
- 公网环境建议在防火墙只放行 80/443，Node 的 3000 端口只监听本机或容器网络。

### 统一认证与服务器拆分（前置）

游戏服已拆出认证适配与在线统计：

- `server/auth.js`：Bearer / HttpOnly Cookie → 一次性 HMAC Ticket
- `server/online-stats.js`：`/api/online`、`runtime/online.json`、`logs/online-*.jsonl`
- `client/auth-client.js`：客户端 Token/Cookie 登录与 Ticket 换取
- `client/runtime-config.js`：`gameServer` / `authApiBase` / `loginUrl` 配置（默认留空即同源部署）

认证信息未定前使用 `AUTH_MODE=dev` 联调；生产使用：

```env
AUTH_MODE=ticket
AUTH_CENTER_URL=https://your-site.example.com
AUTH_INTROSPECT_PATH=/api/game/introspect
GAME_TICKET_SECRET=<long-random-secret>
```

生成可独立部署的服务器目录：

```bash
node tools/build-server-package.cjs   # dist/game-server/
node tools/build-release.cjs         # 桌面最新发布包（client/server/shared/安装包）
```

网站后端可读取 `GET /api/online` 或 `runtime/online.json` 显示在线人数。大媒体与客户端不经过游戏服。

## 桌面版（Electron，可选）

独立外壳，不改现有 Web 版：

```bash
cd desktop
npm install
npm start        # 启动桌面窗口
npm run build    # 生成 desktop/release/ChaosWrithe-2.1.0-portable.exe 与 ChaosWrithe-Setup-2.1.0.exe
```

桌面版默认启动本地服务器用于局域网/离线；正式发布时在 `client/runtime-config.js` 填写远端 `gameServer` 与认证中心地址，客户端会连接远端游戏服，媒体仍由客户端本地加载。

**每次更新后必须重新打包 exe**：只要改动涉及 `server/`、`shared/` 或 `client/`（规则、卡牌、界面、联机逻辑），都要让 `desktop/release/ChaosWrithe-2.1.0-portable.exe` 与 `ChaosWrithe-Setup-2.1.0.exe` 包含最新代码。1.10.0、1.9.0、1.8.0 及更早的 portable exe 作为历史版本保留，不要覆盖。根目录提供一键命令：

```bash
npm run build:all   # build:local + build:engine + build:rules + sync:local + build:exe
```

### 方案7实验结果（默认不启用）

| 平均回合 | 17.4 | 17.5 |
| 平均消灭战斗单位 | 4.0 | 4.0 |
| 平均存活战斗单位 | 12.9 | 12.9 |
| 平均场上混乱层数 | 0.9 | 0.9 |
| 每局混乱崩溃 | 0.0 | 0.1 |

结论：在当前战斗频率和自动出牌策略下，**3 层混乱几乎不会出现**，方案7对节奏和胜负几乎没有影响，因此没有加入正式规则。引擎里只保留了 `createGameEngine({ holyChaos: 'collapse' })` 的实验开关，服务器不会传入。

同时，脚本 AI 只有约 1/6 的对局能在 8 分前结束，多数打满 18 回合后按截止规则决胜，红方胜率也明显偏高。这不一定是真人局的结果，但说明 8 分目标/过半控制门槛可能仍然偏紧；建议先打真人局，再决定是否把目标降到 6 分或放宽 4 格区的控制门槛。

需要注意：
- 这是脚本 AI 的结果，卡牌是自动抽/自动打，不能代替真人手感；如果真人更集中地堆混乱，方案7可能更有存在感。
- 模拟中多数对局打满 18 回合才按截止规则决胜，脚本 AI 很少在 8 分前建立稳定控制。8 分目标是否偏高，建议再用真人局观察；如果仍然普遍打满 18 回合，可考虑把目标降到 6 分，或把 4 格区的控制门槛从 3 格改为 2 格。

## 修改规则时的约定

当前版本以 `client/local/app.js`（规则与热座界面）和 `client/local/index.html`（页面结构）为基准。若后续更新规则：

1. 先更新 `client/local/app.js`（规则唯一修改源；页面/样式分别在同目录 `index.html`、`style.css`）；
2. 运行 `npm run build:engine` 重新生成服务器引擎（抽取基于稳定标记，不再依赖行号）；
3. 运行 `npm run build:rules` 更新规则页；
4. 运行 `npm run sync:local`：先由 `client/local/` 生成离线单文件 `client/local.html`，再同步到 `../现行版本/同步更新单机版.html`；
5. 跑 `npm test`、`npm run test:browser`、`npm run test:browser:animation`、`npm run test:local:animation`、`npm run test:local:standalone` 回归。

**双版本约定**：除非特别说明，功能改动同时应用于联机版与单机版。

只修改联机客户端样式/交互时，不需要动引擎。

**圣辉与矿洞的分层实现**：圣辉的天空层、矿洞的地下层、跨层行动与隐藏视野都以 `client/local/app.js` 为唯一规则源；联机引擎由 `tools/build-engine.cjs` 注入 `getView` 的按视角过滤与服务器指令，单机热座直接调用同一批函数。单机独有的圣辉界面适配放在 `[engine-skip-start]` / `[engine-skip-end]` 标记内，抽取时剔除。修改圣辉或矿洞时需同时更新 `client/local/index.html` 的规则文字与本 README，并运行 `npm run test:holy` / `npm run test:mine` 与对应的 `test:browser:holy` / `test:browser:mine`。
